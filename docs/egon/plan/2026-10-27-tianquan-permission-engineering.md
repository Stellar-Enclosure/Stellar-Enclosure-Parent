# Tianquan 权限工程优化实施计划

状态：部分工程优化和离线验证已完成；完整诊断、真实环境性能及发布验收待完成。以当前工作区中的 Shoubing 身份服务与前端、Jianshen 权限服务与前端为基线，复用 web-sdk、Tianshu、现有 Manifest、Runtime、Outbox 和 CI 工具。实际结果见 [同日期的证据记录](../evidence/2026-10-27-tianquan-engineering/README.md)。

## 目标与不可改变的边界

- 减少业务接入时重复书写后端权限字符与 FIELD/API Key，前端继续显式声明自身资源和引用用途；后端 Manifest 是权限和字段策略的唯一来源。
- 减少已确认的重复计算，并为后续真实环境测量提供可复现的采样口径。当前账号/令牌状态与授权版本仍由现有权威方读取；保留请求输入与方法边界之间的版本比较、独立对象数据范围判定和写入 fence。
- 对拒绝提供可关联的稳定诊断，同时保留外部错误合同和严格审计确认。诊断不得包含 Token、字段值、完整权限集合或其他业务敏感数据。
- 生成可审查的发布计划，保持完整 producer 集合、引用闭包、每个制品的可信资格、CAS、显式激活和旧实例排空。计划输出不是部署证明或自动激活授权。
- 清理只能针对已完成且不再承担重放、回滚或审计证明责任的数据；沿用既有清理、重试和告警组件。
- 不启动服务、数据库、容器或浏览器；不执行真实注册、激活、数据删除、迁移或发布。保留用户已有工作区修改，不触及旧迁移。计划中的性能数值只有真实受控环境采集后才能标为实测。

## A. 接入工具与试点

1. 使用 Jianshen `RolePermissionGrantController`、`ReplaceRolePermissionsRequestDTO` 和 `RolePermissionGrantPage` 作为试点，记录权限字符、资源 Key、5 个字段引用和开发命令的现状。
2. 扩展 SDK 现有 Node CLI，从已固定摘要、完整性可核对的后端 FULL Manifest 生成确定性的 TypeScript 引用。验证应用和 producer 身份、资源类型、重复/缺失 Key、合同 schema、输入摘要；输出只含引用，不导出新定义或推断授权。构建前生成，扫描器和 TypeScript 能静态解析，失败不得使用旧产物。确认输入来源与制品证明的边界：本地摘要校验不是受信部署资格。
3. 前端显式保留 BUTTON、FORM_FIELD 等用途，从生成引用中取权限字符和 Key；基于固定 Manifest 构建期校验。新旧声明方式兼容，普通构建不发起注册或角色授予。尽可能复用 `build-consumer` 的本地/CI 入口。
4. 合并重复配置和脚本只在不削弱 SDK 固定版本、目标、protected environment、资格及权限授予校验的条件下进行；不能因本地工具仍未固定为生产 commit 而虚构生产 pin。

验收：生成结果确定且无法手工替换 Manifest 生效；缺失、错误 producer、内容或摘要不符时失败；现有 AST 扫描、产物校验、前端授权/字段测试通过；记录试点实际修改文件数、重复字符串数与命令数。

## B. 请求链与可观测性

1. 盘点 `AuthorizationSnapshotLoader`、`PermissionExecutionGuard`、`PermissionExecutionContext`、`PermissionFieldBindingGuard`、Runtime 快照仓库和 IdP 权威/审计客户端的真实调用路径。
2. 首先消除单个字段绑定或快照计算内重复的纯计算和元数据遍历，不缓存账号有效性、不跳过跨授权边界读取，不改变 SERVICE 逐字段复验点。仅在边界和时间语义被回归证明等价时复用事实。
3. 复用已有观测接口记录低基数的授权阶段、结果和耗时；将 SQL 次数、远程调用次数、审计保存/回执、请求鉴权 P95/P99 的采集方法及四类场景写入证据模板，不把模拟或 mock 当实测。
4. 若复用角色权限快照涉及定时授予、未来生效、目录版本或事务一致性，必须证明精确有效期和同事务一致性；当前快照信息不足时保留重算。

验收：现有 USER/SERVICE API、字段保护、scope、快照读取、输入 checkpoint、撤权和 fence 测试通过；新增针对实际减少的计算或诊断的测试。真实 DB/网络 P95/P99 以用户提供的已运行隔离环境完成，缺失时标记 NOT_RUN。

## C. 拒绝诊断和候选策略影响

1. 保留现有外部状态码、错误和审计确认；在内部观测中区分 OAuth scope、业务权限、资源绑定、数据范围和 Runtime 不可用等已知原因，并通过服务端生成的 decisionId/traceId 关联；不把隐藏字段或权限细节返回给普通调用者。
2. 复用 `PermissionManifestDiff` 和现有 simulation，增强候选与当前策略的解释和影响展示。只读模拟不执行业务操作；允许按现有要求审计模拟行为。
3. 记录诊断证据和版本与原请求的关联；历史证据缺失时明确显示无法还原，不将当前状态伪装成历史。

验收：对 scope 缺失、权限缺失、版本/制品不一致和数据范围拒绝分别有可辨认的内部证据；新增资源复用既有授权、ALL→ANY、字段读写扩展均被 Diff 标记；非授权人员无法查询其他用户权限细节。

## D. 发布计划

1. 根据已验证的当前 descriptor、完整候选/旧 Manifest、引用和资格信息生成只读计划，列出改变的 producer、复用的版本、需构建/部署/重新取得资格的项、语义变化及风险。
2. 检查同一 catalog scope、producer 完整集、FULL、权限和资源引用闭包、预期激活修订和每个资格的时间与绑定。缺失证明、未知 API 兼容性、资格过期或 Diff 不确定时明确 BLOCKED/需人工确认，不能报告安全或提交激活。
3. 输出 readiness、旧实例停止接流/排空、显式激活、切流和验证顺序。旧资格过期时复用旧制品但重新取得资格，不虚构证明。
4. 使用前端单独变化与后端单独变化两种固定场景验证：一个候选版本、一项旧版本复用、完整集合提交不缺项；涉及已有权限扩大的候选不应自动通过。

验收：CLI 和服务端原有资格、引用、CAS、Diff 及 activation 测试通过；两场景的离线计划和负面测试有可重放证据；实际部署/流量切换需要已有受信环境。

## E. 生命周期和审计

1. 列出 OAuth 短期事务、refresh/token family、幂等回执、授权快照、Outbox、Inbox、dead letter、审计的保留依据和清理负责人。
2. 检查现有清理对未解决死信、未完成操作及引用快照的保护；在有明确状态/证明前保守保留。优化积压与失败的低基数观测和重试，不先引入新存储或分区。
3. 报表/索引/归档允许异步；必须在放行前持久化或确认的事件仍保持原确认点。

验收：清理单元/SQL 条件测试包含未完成、并发更新、重放保护、当前激活及回滚引用；不对真实数据执行清理。实际增长及告警阈值在受控环境观测后制定。

## 后续任务：按 decisionId 查询拒绝

1. 在现有 Jianshen Starter 的拒绝审计点发出最小、不可变的进程内诊断事件；复用 Spring 事件机制，不能携带 Token 或业务字段值。原 IdP 严格审计确认和拒绝结果保持不变；辅助诊断写入失败只能报告失败，不能改变授权结论。
2. Jianshen Admin 复用现有 append-only 审计表记录本机 USER API 的决策编号、原因、规则、授权/目录/制品版本、相关权限是否存在及通过 Scope 限定。采集活动角色及权限关联时，以原决策快照时间和版本为依据，使用权威 SQL 锁顺序；若当前版本不再一致或事实不足，明确标记来源不可还原，禁止以当前角色推断历史。
3. 在已有、由 `system:audit:read` 保护且按当前租户限定的审计查询和管理页面中增加 decisionId 过滤和可读详情。不得根据调用方提供的租户查询其他租户，也不得将解释返回普通被拒绝的用户。
4. 覆盖 scope 缺失、业务权限缺失、角色来源、版本竞争、无权限和跨租户、持久化失败与旧审计记录的回归。保留现有 SQL/审计语义，不启动服务或浏览器。跨服务汇聚、真实数据库事务和运行验收必须单独标识；不得把进程事件当成跨服务的持久投递。

执行结果：本机 USER API 的 scope / permission 拒绝、当前角色与直接授予来源、当时目录 / 账号 / 策略及制品版本已经接入原审计页面；当快照版本已变化或读取失败时来源标记为不可核实。定向测试覆盖严格回执失败、事件装配、事务完成后的独立写入、查询权限声明及租户过滤；它们不替代真实 HTTP、PostgreSQL 并发及跨租户访问验收。此前失败的 token 验证、身份冻结、字段/数据范围、制品绑定和其他服务内的拒绝尚不保证有这条本地诊断记录。

## 后续任务：字段、数据范围与制品绑定诊断

1. 沿字段实际绑定拒绝点提取已声明 FIELD Key、写入规则、scope、只读绑定和决策时快照；不记录输入值、未知字段名，也不改变公开错误、字段检查或写入 checkpoint。读取字段的脱敏/省略是正常投影，不伪造为请求拒绝。
2. 在 USER API/FIELD 的制品绑定拒绝点，在快照确实属于配置的可信 scope 和当前身份时，记录执行侧与 Runtime 选定的 producer/digest、未通过的绑定条件、可用版本；不从失配快照计算角色来源。无可信快照或跨 scope 时不推断历史授权。
3. 数据范围复用已有 `decideDataScope` 和严格审计装饰器：只在默认决策器取得其实际快照、返回 DENY 且现有审计交接成功时记录范围策略判定，明确它不代表逐对象最终判定；不记录目标业务对象或组织/用户列表，不重放判定，也不修改 fence。自定义决策器、未启用审计交接或无法确认快照时明确不保证该记录。
4. 扩充当前审计详情兼容旧记录，展示诊断类型、字段规则、数据范围策略或部署摘要差异。保留现有查询权限/租户隔离和失败回退。
5. 覆盖字段 scope/permission/只读、严格回执失败、绑定各摘要差异与跨租户/未知 scope、数据范围 DENY/ALLOW/INDETERMINATE 和真实对象边界仍由业务判断；运行离线测试、构建/Manifest 对比。真实 PostgreSQL、服务、浏览器与并发验收继续单独记录。

执行结果：已实现上述本机路径；前置 Runtime 绑定失败通过内部异常原因携带经本机 Runtime 获取的元数据，原 USER 经认证且现有严格审计交接成功后才生成编号并发布辅助证据。范围策略的中间 DENY 不表示业务最终拒绝，明文/脱敏/省略读取不生成拒绝。自定义决策器、未确认交接、在获取可信快照之前由远端 Runtime 或身份入口拒绝，以及无声明的字段输入，仍不保证生成可查询记录。真实数据库事务及端到端环境状态为 NOT_RUN。
