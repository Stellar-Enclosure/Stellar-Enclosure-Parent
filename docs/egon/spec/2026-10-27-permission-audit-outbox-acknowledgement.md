# 独立设计：审计持久化与远端处理解耦

状态：设计草案，不在本轮实施。当前 Token 使用审计要求权威接收方返回匹配的已提交 SQL 回执；不能以进程内队列或本地异步提交替代。

## 触发条件

先在相同环境测量四类请求的本地持久化、远端投递、回执等待及鉴权 P95/P99。只有回执等待是明显瓶颈、业务接受确认责任迁移且具备可靠 PostgreSQL owner 时，才考虑改变合同。

## 候选合同

1. 明确本地 PostgreSQL owner、数据库职责、故障域和保留期。放行之前必须在该 owner 上提交完整审计事件及其 Outbox；成功响应携带稳定 eventId、内容指纹和 owner 提交证明。任何提交失败、数据库不可用或无法确认提交均拒绝。
2. dispatcher 按现有 Outbox 租约、重试和死信机制异步投递；远端以 eventId 和指纹幂等去重，相同 ID 不同内容视为冲突。原记录在远端接收证明、恢复与审计保留条件满足前不得删除。
3. 定义事件最大积压、最老未完成事件年龄、重试/死信率和磁盘阈值；越过硬上限时暂停放行并告警。恢复过程可以重放已提交事件，不丢弃失败事件，也不能以内存排队作为持久化成功。
4. 明确本地提交后的崩溃、远端已写但回执丢失、重复投递、数据库恢复和跨区域故障的责任与运维操作。对调用方暴露的确认语义须版本化，记录从“远端确认”变为“本地持久化”的准确时点。

## 迁移与回滚

先保持原严格回执，双写并比对本地记录与远端回执，不改变放行判断；再在隔离环境验证故障恢复、去重和持久性，逐个资源显式启用新合同。回滚时停止新增本地确认并排空/核对所有待投递事件，恢复远端确认；禁止删除旧事件或跳过未完成回执。任何 schema 调整仅使用新迁移。

## 验收

测试提交前断电、提交后进程退出、网络隔离、远端重复、回执丢失、数据库恢复、容量耗尽、告警和权限隔离；核对事件总数、指纹及提交顺序。对比严格模式和候选模式的 P95/P99、故障期间拒绝行为及恢复时间，只有可证明的收益和可接受的责任变化才能推进。
